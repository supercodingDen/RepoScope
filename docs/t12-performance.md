# T12 scale and retrieval evaluation

T12 uses 100,029 source-located chunks from 4,782 distinct public Python source paths (49,152,059 source bytes). The database contains 4,708 distinct file hashes and 71,742 distinct chunk-text hashes; identical real snippets are retained at their separate source locations, without replaying files or generating source. The corpus fingerprint is `6bfb40572e297039d0c800e3dc0b7e8e0ffda363ca37906105ca5fd2b94254e2`. The source is CPython 3.12.14 `Lib` and `Tools`, plus packages installed from this repository's `uv.lock` (SHA-256 `887563520b1290f7049f812d12b367188780d245ad52c4b283cee4459d66dd35`). The official [CPython source archive](https://www.python.org/ftp/python/3.12.14/) was checked against SHA-256 `5c8462af5790baf43a321a1559dbe0db06d1be4300fb85fb53c40060668e548a`. Source content is not redistributed.

The [fixed manifest](../bench/data/t12-corpus.json) contains 200 deterministic code-location questions with source-path labels. These are fixed performance inputs, not human-reviewed semantic relevance judgments. Chunks and queries use the versioned mock SHA-256 384-dimensional embedding space. No provider request or paid API call was made. ANN Recall@10 compares vector neighbors with exact cosine neighbors; it says nothing about whether the model understands a code question.

## Environment and method

The local host was an Intel Core i9-14900HX with 32 logical processors and 31.7 GiB RAM. Docker Desktop 29.8 ran Linux x86-64 PostgreSQL 17 with pgvector 0.8.6; the isolated database container was limited to 8 CPUs and 12 GiB RAM with 2 GiB shared memory. Docker exposed 15.47 GiB total memory, so this is **not** the roadmap's exact 8-vCPU/16-GiB Linux reference host. No development PostgreSQL or JetStream volume was used. The benchmark loader inserted one clearly labeled composite generation solely to exercise the production retrieval tables and SQL. Its acquisition and bulk load are not a claim that a single production ingestion job can finish 100K chunks within its 30-minute deadline.

The vector profile used all 200 queries, exact ground truth, ef_search values 40/80/120/200 and additional tuning values, ten warm-up queries and three measured trials. The application profile used the same query set with 32 continuously active clients for 60 seconds per trial after warm-up. Every successful request latency was retained; errors were counted separately. Results are client-observed application calls to `RetrievalService` with local mock query embedding. They are neither external HTTP latency nor live-provider text-search latency. The exact query, generation filter, model space, corpus, and hardware were held fixed. Cache state was not forcibly reset between phases, so cross-phase latency changes include warm-cache effects. The first application comparison used a 32-connection benchmark pool to expose database saturation; the production API config uses ten connections, which is reported separately. The batch experiment separately tried limits of 8/16/32 and concurrency 1/2/4 on 1,009 real chunks, with three measured mock-embedding trials per combination; it did not write to PostgreSQL.

## Measured changes

| Before: repeated generation count, HNSW m=16, ef_search=80, pool=32 | 367.072 / 370.891 / 357.075 | 101.183 / 101.421 / 101.940 | 0.116 | 8.631 / 10.172 / 10.294 |
| Store published generation count, HNSW m=16, ef_search=80, pool=32 | 393.830 / 439.324 / 506.084 | 97.369 / 93.397 / 70.618 | unchanged | unchanged |
| Store count, HNSW m=64, ef_construction=400, ef_search=400, pool=32 | 38.864 / 38.982 / 38.992 | 899.901 / 896.918 / 897.409 | 0.913 | 59.334 / 59.903 / 58.957 |
| **Shipped:** store count, HNSW m=64, ef_construction=400, ef_search=420, pool=10 | **79.762 / 80.173 / 80.046** | **444.611 / 438.126 / 442.384** | **0.9235** | **67.946 / 69.362 / 67.084** |

The first change stores an immutable generation's chunk count when publishing it, avoiding a full `count(*)` on every active or pinned search. Existing rows are backfilled and older staged rows retain a counted fallback. The first post-change trial still shows cache warming; all three raw trials are retained to make that visible.

The second change raises HNSW connectivity and construction effort, then uses ef_search=420. Against the same exact neighbors, the three unfiltered recall trials were all 0.9235 and their database-only vector p95 stayed below 75 ms. The `cpython/` path filter covered 33,194 chunks; its three recall trials were all 0.917 and p95 was 67.601/67.656/66.931 ms. At ef_search=400 the filtered recall was only 0.899; at 500, filtered vector p95 exceeded 75 ms. Building the m=64 index took 359.223 seconds on this machine and produced a 257 MB index. The production-sized pool met the 50-QPS target but missed the 100-ms search p95 target. The benchmark therefore does **not** claim the complete roadmap performance gate has passed.

A stored full-text-vector experiment was also measured, then rejected: after the count change its three search p95 values were 94.061/98.123/97.426 ms and QPS was 414.370/374.941/375.316. It regressed against the count-only configuration, so that migration and query change were removed. Its raw result remains in the evidence for auditability.

An inner-product HNSW experiment was also rejected. pgvector [recommends inner product for normalized vectors](https://github.com/pgvector/pgvector#querying), but with this corpus and identical m=64/ef_construction=400/ef_search=400, it produced Recall@10 of 0.912 and median DB vector p95 of 59.594 ms, versus cosine's 0.913 and 59.334 ms. Its index took 370.107 seconds to build. The measured difference did not justify another index or operator change.

At ef_search=400 the HNSW scan itself took about 64 ms in a production-shaped `EXPLAIN ANALYZE` and returned all 50 vector candidates; the lexical query took about 0.1 ms for the sampled question and returned no matches. No exact underfill fallback occurred. With 32 active SQL connections the 8-CPU container saturated, explaining why serial vector latency cannot be substituted for concurrent application latency.

## Boundaries still requiring evidence

The local mock space is a stress-test vector distribution, not a real semantic embedding evaluation. Live query-embedding latency, human-reviewed answer relevance, external authenticated HTTP search, full-agent orchestration overhead, the 30-minute single-job 100K ingestion gate, and the 100-ms search target remain open. The existing redelivery tests assert idempotent committed results but were not repeated during this 100K load. The isolated database had no OOM and every measured search phase had zero request errors. A separate real loopback HTTP profile of the development API's `/healthz` endpoint, limited to one CPU, used 32 clients and 2,000 requests per trial: p95 was 83.375/82.965/141.568 ms, with zero errors. It does not pass the 30-ms non-search target and is not comparable to the 8-CPU isolated database profile.

Raw per-query and per-request observations are preserved in the [compressed archive](../bench/data/t12-raw-evidence.zip) with a [SHA-256 index](../bench/data/t12-raw-index.json). The benchmark programs are in `bench/` and cover corpus creation, isolated loading, retrieval measurement, batch trade-offs, SQL plans, HTTP health, and deterministic archiving. Reproduction requires the exact CPython release, packages installed with `uv sync --frozen --all-groups`, the same source fingerprint, and an isolated migrated PostgreSQL instance. The loader's `--baseline-index` flag recreates the original m=16 index; the default builds the tuned m=64 index. Set `T12_PYTHON_LIB`, `T12_PYTHON_TOOLS`, and `T12_SITE_PACKAGES` to the local source paths. The loader requires `T12_DISPOSABLE_DATABASE=1`, an empty database, and `T12_DATABASE_URL=postgresql://reposcope_migrator@127.0.0.1:15432/reposcope`; it rejects other targets. Never point benchmark programs at a development or production database.
