# Public repository readiness

This record separates publication of GitHub source from hosting the API. The owner chose to make the existing `supercodingDen/RepoScope` repository public, including its commit-author metadata. No API credential belongs in Git, a release asset, an Actions variable, or a screenshot. Future live credentials must be created and mounted from protected host files after hosting is selected; see [manual configuration](manual-configuration.md).

## Controls delivered with the source

- `.gitignore` and `.dockerignore` exclude standard dotenv files, credential basenames, key formats, and secret directories. Ignore patterns are a safety net, not a security boundary.
- `scripts/publication_guard.py` fails the `secrets` CI job if a tracked credential path or populated secret value in `.env.example` appears. The same job scans all fetched branch/tag references and a temporary copy of tracked files (including one level of archives) with redacted Gitleaks. Checkout does not persist credentials. The `security` job scans source and images with Trivy; all four `quality` jobs must pass on the final commit. The release workflow now scans regular files from every image layer before upload and fails closed on recognized secrets; this gate applies to a future release source commit containing the updated workflow and scanner.
- Production Compose reads database/API/provider credentials from host-mounted files under `REPOSCOPE_SECRETS_DIR`; `compose.production.live.yaml` is required only for explicitly enabled paid mode. Do not place those files in the checkout or GitHub Actions secrets for this publication task. The current PostgreSQL Dockerfile removes the upstream snakeoil key and certificate from its final filesystem, and CI checks both paths are absent. Immutable upstream layers may still contain the historical test key, so do not distribute a new image archive without a full layer-level audit.

## Owner-controlled GitHub settings

1. Open **Settings → Rules → Rulesets** and add an active branch ruleset targeting `main`. Require a pull request, current `python`, `containers`, `secrets`, and `security` checks, and block force pushes and deletions. Use zero required approvals for a solo owner until a reviewer exists; do not create an impossible approval requirement. Restrict `release/*` changes and tag creation to trusted maintainers. Verify the resulting `main` branch reports protected. On GitHub Free, neither rulesets nor branch protection are available for a private repository: finish every other audit gate while private, switch visibility, then immediately activate and verify protection as the first public action. Alternatively, upgrade to a plan that permits private-repository protection and configure it before switching visibility. If protection cannot be activated after the switch, return the repository to private while you resolve the limitation.
2. Confirm the three retained release SBOMs pass the final asset audit and review any newly available Actions material. Review the repository's **Security and quality → Advanced Security** settings. Resolve any actual secret alert before publication. Recheck latest source SHA and four green jobs.
3. Only after the audit and final checks use **Settings → General → Danger Zone → Change repository visibility → Public**. The GitHub integration used here cannot perform this administrator operation. GitHub warns that code, Actions history, and logs become publicly visible. A visibility change may disable push rulesets; activate or recheck all protections immediately afterward, according to the account-plan path above.
4. Enable available secret scanning, push protection, Dependabot alerts, and code scanning under **Advanced Security**. Enable **Private vulnerability reporting** and subscribe to security notifications. Do not bypass a legitimate secret alert to make CI green.
5. From a signed-out session, inspect source, commit history, release assets, and Actions. Confirm the final SHA and four `quality` jobs, settings, and absence of accidental credentials. Record the public URLs and date in [acceptance](acceptance.md) and [project status](project-status.md). Keep the service-hosting gate separate: no VM, domain, or live provider is configured by publishing the repository.
